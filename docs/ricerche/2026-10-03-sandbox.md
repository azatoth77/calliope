# Sandbox degli agenti: isolamento vero sulla DGX (03/10/2026)

Il codice scritto dall'agente girava con l'utente di Calliope, protetto da un audit hook (che
la PEP 578 non considera un confine di sicurezza) più i limiti di risorse. Sulla DGX Spark
(Ubuntu 24.04 aarch64, DGX OS) serviva un confine vero. Misure fatte sulla DGX, senza sudo e
senza toccare i container esistenti.

## 1. Cosa c'è sulla DGX

| | Esito |
|---|---|
| Docker | 29.6.2, **rootful** (demone di sistema, runc, cgroup v2, driver systemd); l'utente è nel gruppo `docker`; seccomp e AppArmor attivi |
| `apparmor_restrict_unprivileged_userns` | **1**: le user namespace non privilegiate sono limitate da AppArmor |
| bubblewrap (`/usr/bin/bwrap --unshare-all …`) | **non va**: `loopback: Failed RTM_NEWADDR: Operation not permitted` |
| `unshare -rn true` | **non va**: `write failed /proc/self/uid_map: Operation not permitted` |

bubblewrap e `unshare` richiederebbero un profilo AppArmor dedicato (sudo) o di abbassare la
restrizione per tutta la macchina: scartati. Resta **Docker**, che c'è già ed è usato senza
sudo.

## 2. Scelta: un container usa-e-getta per ogni esecuzione

`docker run --rm -i` per ogni `esegui_python` ed `esegui_test`, dall'immagine
`calliope-sandbox:<prime 12 cifre dello SHA-256 del Dockerfile>`:

| Opzione | Perché |
|---|---|
| `--network none` | solo loopback: nessuna connessione, nessun DNS |
| `--read-only` + `--tmpfs /tmp:noexec,nosuid,nodev,size=16m` | il disco dell'immagine non si scrive; in /tmp non si esegue niente |
| `--mount` della sola cartella del lavoro in `/lavoro`, `_avvio.py` in sola lettura | nient'altro dell'host è visibile; lo script di avvio segue la versione di Calliope senza ricostruire l'immagine |
| `--user <uid>:<gid>` di Calliope (65534 se fosse root) | non root; i file scritti restano dell'utente |
| `--cap-drop ALL`, `--security-opt no-new-privileges` (+ seccomp e AppArmor predefiniti) | CapEff 0, niente setuid |
| `--memory` = `--memory-swap` = `agenti_memoria_mb`, `--ulimit data=` uguale | il tetto vero è il cgroup; RLIMIT_DATA fa arrivare un `MemoryError` leggibile all'agente invece di un'uccisione |
| `--pids-limit 32`, `--cpus` (`agenti_sandbox_cpu`, 2), `--cpu-shares 256` | fork bomb e CPU: la voce non perde il processore |
| `timeout -s KILL <tempo+5>` dentro il container | se Calliope muore (il client docker muore con lei, il container no: è figlio di containerd, non del cgroup del servizio) il container si ferma da solo |
| `docker kill <nome>` a fine tempo e all'annullo | il client docker non si uccide: lascerebbe vivo il container |
| `--pull never`, `--log-driver none`, solo variabili scelte con `-e` | niente download a sorpresa, nessun log su disco, nessuna variabile dell'host (token, SSH) |

L'**audit hook** resta dentro il container come seconda linea: i messaggi «Bloccato dalla
sandbox di Calliope» all'agente non cambiano.

Immagine (`setup/linux/sandbox/Dockerfile`): `python:3.12-slim` con numpy 2.5.3, openpyxl
3.1.5, python-docx 1.2.0, fpdf2 2.8.9, PyYAML 6.0.3 (le versioni di `uv.lock`), senza pip;
**288 MB**, costruita in 9 s con la rete. Si costruisce con `calliope motore sandbox
costruisci` (chiede conferma), proposto anche da `installa.sh` se Docker c'è.

## 3. Misure (DGX, 03/10)

| | Mediana |
|---|---|
| `docker run` dell'immagine con `true` | 0,15 s |
| esecuzione di uno script con tutte le opzioni sopra (shell) | 0,18–0,22 s |
| `Sandbox.esegui` con il container (10 volte, due giri) | **0,17–0,22 s** |
| `Sandbox.esegui` con il motore «processo» (10 volte, due giri) | 0,04–0,06 s |
| `Sandbox.test` con un test nel container | 0,17–0,22 s |
| scelta del motore (`docker image inspect`) | 13–21 ms |

**+0,12–0,18 s per esecuzione**: un lavoro di codice ne fa qualche decina, contro passate del
modello da secondi. Accettabile.

`prove/prova_sandbox.py --docker` (Docker vero, 12 s), tutte passate:
- con l'audit hook, dentro il container: rete (socket, urllib), lettura, scrittura ed elenco
  fuori, subprocess, os.system, ctypes (memoria e dlopen), sottointerpreti, chdir fuori,
  fork, fork bomb, posix_spawn, execv; `MemoryError` a 3 GB; tempo scaduto in 5,1 s con il
  container rimosso; ambiente pulito; openpyxl, python-docx e numpy funzionano; i file sono
  dell'utente; i test girano;
- **senza audit hook** (`python -c` nello stesso `docker run`): interfacce solo `lo`;
  connessioni a 1.1.1.1, 8.8.8.8, al bridge di Docker e alla LAN tutte `ENETUNREACH` (101);
  DNS assente; scrittura in /usr, /etc, /, su `_avvio.py` → `EROFS` (30); uno script in /tmp
  non si esegue (`EACCES`, 13); `/lavoro` scrivibile; la home dell'host e il socket di Docker
  non esistono; uid non 0, `CapEff`/`CapBnd` 0, `NoNewPrivs` 1, `Seccomp` 2; fork bomb
  fermata a 30 processi (`EAGAIN`); numpy da 3 GB → `MemoryError`.
- `prova_agenti.py` intera sulla DGX: il lavoro di codice con l'Ollama finto gira nel
  container (scelta «auto»), la capacità dice «il codice gira in un container Docker…».
  Trovato e corretto nel motore «processo» su Linux: openpyxl non si importava (mimetypes
  legge `/etc/mime.types` dopo l'hook); ora `_avvio.py` lo inizializza prima.
- Calliope uccisa con `kill -9` durante un ciclo infinito (tempo 3 s): il container è ancora
  vivo dopo 2 s, sparito (e rimosso) entro il timeout interno di 8 s.

## 4. Cosa resta

- Il confine è il kernel condiviso (namespace, cgroup, seccomp), non una macchina virtuale;
  il container ha l'uid di Calliope, quindi un'evasione avrebbe i suoi permessi. Un passo in
  più sarebbe gVisor (`--runtime runsc`) o un uid dedicato senza file sull'host (con il mount
  della cartella scrivibile da quell'uid), oppure Docker rootless con userns-remap.
- L'utente di Calliope nel gruppo `docker` vale root sull'host: era già così per l'utente
  della DGX; il codice dell'agente non vede il socket.
- Su Windows (il portatile, oggi solo satellite) resta il motore «processo».
- `FROM python:3.12-slim` non è fissato per digest: ricostruendo si prende l'ultima 3.12-slim;
  il nome dell'immagine cambia solo con il Dockerfile.
